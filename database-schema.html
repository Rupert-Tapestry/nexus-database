01How to read this

Two schemas live in this database. Nexus is the off-the-shelf Invision Community commerce application — 54 tables, none of them ours. The rest is the custom schema written in-house for Tapestry and the FSF community: 12 tables, plus five columns grafted onto a Nexus table.

Conventions

ConventionDetail
Table prefixEvery table carries the installation prefix. This install uses ibf_ (see upgrade_insert.sql), so nexus_invoices is physically ibf_nexus_invoices. Prefixes are omitted throughout this document, as they are in the code.
Column prefixIPS ActiveRecord models declare a $databasePrefix and then drop it in PHP. $purchase->expire is ps_expire; $school->name is school_name. The prefix for each custom table is given in its section.
TimestampsINT(10) UNIX timestamps, not DATETIME. 0 conventionally means "never" or "not yet", not 1970.
MoneyDECIMAL(20,2) for stored totals; JSON {currency: amount} maps where a value is per-currency (p_base_price, t_rate).
JSON columnsStored as TEXT, not the MySQL JSON type. Some of the oldest rows hold PHP-serialised arrays instead — nexus_invoices.i_items is the one that actually bites, and Promise::getPurchases() has a fallback branch for it.
BooleansTINYINT(1), 0/1.
Foreign keysThere are none declared at the database level. Every relationship in this document is a convention enforced in PHP, so orphaned rows are possible.

Where this came from

Column names, types, nullability, defaults and indexes are generated from the applications’ own data/schema.json files — the same files the installer runs. Descriptions are written from the code that reads and writes each column. Nothing here was checked against a live database: there is no conf_global.php in the repository.

Two tables — tapestry_schools and tapestry_trials — predate the current schema files and appear in no schema.json at all. Their columns are reconstructed from the code and their types are marked as inferred. §9 lists everything else that has drifted.

02The shape of it

The commercial spine, left to right: a customer buys a package, which raises an invoice, which is settled by a transaction, which creates a purchase. The purchase is the subscription, and everything Tapestry cares about hangs off it.

       │                ├──── nexus_customer_cards
       │                ├──── nexus_alternate_contacts

tapestry_schools custom not in schema.json

Column prefix school_ · model \IPS\tapestry\Schools · applications/tapestry/sources/Schools/Schools.php

The local record of a Tapestry setting, and the join between the two systems. One row per setting, keyed by the same integer Tapestry uses, pointing at the Nexus purchase that pays for it.

Only a stub of the setting is held here. 05Custom columns on Nexus

The Tapestry application adds five columns to nexus_support_requests. They implement the non-EU data-residency control: support staff working outside the EU may only see a ticket if every setting involved has consented to non-EU processing.

ColumnTypeNotes
r_non_eu_statusINTThe computed answer. 0 not yet checked · 1 visible to non-EU staff · 2 not visible · 3 needs recheck. Only 1 is visible; everything else fails closed. Written by the checksupportrequests task (which picks up 0) and the rechecksupportrequests task (which picks up 3).
r_non_eu_status_changed_atINTUnix timestamp the computed status last changed.
r_non_eu_overrideINTStaff override. 0 no override · 1 force visible · 2 force hidden. Takes precedence over r_non_eu_status entirely. Only staff with the tapestry / eu / staff_working_in_eu ACP restriction may set it.
r_non_eu_overridden_byINTFK → core_members.member_id — who set the override.
r_non_eu_overridden_atINTUnix timestamp the override was set.

How the check runs

  ticket raised  (r_non_eu_status defaults to 0)
        │
        ▼
  checksupportrequests task  — picks up r_non_eu_status = 0, 10 at a time
        │
        ├─ r_member > 0 ? ── the member, plus every account they are an
        │                    alternate contact for (nexus_alternate_contacts,
        │                    alt_id = member) — and all of their email addresses
        └─ r_member = 0 ? ── just r_email
        │
        ▼
  resolve that to a set of settings, three ways, merged:
        · tapestry_schools.school_admin_id  IN (members)          — settings they own
        · via nexus_purchases.ps_member     IN (members)          — settings they pay for
        · Tapestry API searchForEmailAddresses                  — settings by email
        │
        ├─ found some ──▶ write tapestry_support_request_schools (replacing any
        │                 existing rows), then r_non_eu_status = 1 if EVERY
        │                 setting has consented, else 2
        │
        └─ found none ──▶ r_non_eu_status = 2, UNLESS the ticket is in the
                          designated non-EU department, in which case 1
        │
        ▼
  r_non_eu_status_changed_at = now


  setting changes its consent in Tapestry
        │  POST /tapestry/settingdetails/{id}
        ▼
  every ticket linked to that setting via tapestry_support_request_schools
        │  ──▶ r_non_eu_status = 3
        ▼
  rechecksupportrequests task — picks up 3, re-runs the same resolution, back to 1 or 2

At read time, visibleToNonEuAdmin() returns r_non_eu_override == 1 if an override is set, otherwise r_non_eu_status == 1. Staff without the EU restriction get this spliced into every support stream query:

(r_non_eu_override = 1 OR (r_non_eu_override = 0 AND r_non_eu_status = 1))

Two things to know before you query these

The resolution is a merge across all three paths, and a single non-consenting setting anywhere in that set drops the whole ticket to 2.

The nexus_alternate_contacts lookup is not filtered on billing or support — any alternate-contact relationship pulls that account’s settings into the decision.

Undeclared

These five columns are in no applications/nexus/data/schema.json and in no tapestry/setup upgrade step. They were added to the live database directly. See §9.

09Schema drift

The shipped schema.json files no longer describe the live database. Everything below exists in production but has no schema definition, which means a clean install from this codebase would not produce a working database.

WhatWhere it should beNotes
tapestry_schools (whole table)applications/tapestry/data/schema.jsonPredates the current schema file. The one column added properly since — school_status_changed_at, in setup/upg_31009 — targets a table the installer would never have created.

tapestry_packages.wondeapplications/tapestry/data/schema.jsonSchools::packages() filters on wonde (0 standard · 1 paid Wonde · 2 free Wonde). The schema file defines only id and children.
nexus_support_requests.r_non_eu_status and the other four r_non_eu_* columnsa tapestry/setup upgrade stepAdded to the live database directly, in the application that needs them or in Nexus — either would do, but neither was done.
applications/tapestry/setup/upg_20000/queries.json—Invalid JSON. The object's last two entries are written as bare { ... } with no key, which no JSON parser accepts. json_decode returns NULL, so the whole step is a no-op: tapestry_globalpay, tapestry_api_log.api_failed and its index are never created on an upgrade path. All three are in schema.json, so a fresh install does get them — it is only sites upgrading through this version that would be left without them.

None of this is urgent while the database exists. It matters the day someone tries to stand up a fresh environment, and it matters to anyone reading schema.json expecting it to be the truth.

10Cheat sheet

The joins you will actually write.

-- A setting, its subscription, its size and its owner
SELECT s.*, p.ps_expire, p.ps_active, p.ps_cancelled, t.children, m.name, m.email
FROM      tapestry_schools  s
LEFT JOIN nexus_purchases   p ON s.school_pkg_id = p.ps_id
LEFT JOIN tapestry_packages t ON p.ps_item_id    = t.id
LEFT JOIN core_members      m ON s.school_admin_id = m.member_id;

-- Live promised payments, with the invoice being held open
SELECT pr.*, i.i_total, i.i_status, s.school_name
FROM      tapestry_promised pr
JOIN      nexus_invoices    i ON pr.promise_invoice_id = i.i_id
LEFT JOIN tapestry_schools  s ON pr.promise_school_id  = s.school_id
WHERE pr.promise_actioned = 0
  AND pr.promise_date_expire > UNIX_TIMESTAMP();

-- Tickets a non-EU staff member may see
SELECT r.*
FROM nexus_support_requests r
WHERE r.r_non_eu_override = 1
   OR (r.r_non_eu_override = 0 AND r.r_non_eu_status = 1);

-- Which settings a ticket touches, and whether each has consented
SELECT r.r_id, s.school_id, s.school_name, s.school_non_eu_processing_consent
FROM tapestry_support_request_schools m
JOIN nexus_support_requests r ON r.r_id      = m.request_id
JOIN tapestry_schools       s ON s.school_id = m.school_id;

-- Members with current LA membership
SELECT m.member_id, m.name, la.la_title, h.rexpiredate
FROM      foundation_group_upgrade_history h
JOIN      core_members  m  ON m.member_id = h.ruserid
LEFT JOIN foundation_la la ON la.la_id    = h.rkeyid
WHERE h.rexpiredate > UNIX_TIMESTAMP();
